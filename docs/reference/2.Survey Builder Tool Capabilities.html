Survey Builder — Capabilities

A reference of everything the form builder can currently model, configure and produce.

1 Overview

The builder is a visual, drag-and-drop tool for authoring field surveys. A form is built once in English and then translated; the Android field app and printed training material are generated from the same schema.

  • Author sections and questions across 20 input types with rich per-question configuration.
  • Control flow with skip logic (visibility) and repeating rosters.
  • Quality with validation rules and High-Frequency Checks (HFC / form-checks).
  • Localize into Hindi, Marathi, Gujarati and Kannada (AI-assisted + manual).
  • Produce a language-specific mobile schema, a printable enumerator training document, and standard exports (XLSForm, XML, JSON).

2 Survey Structure

Every survey follows a simple nesting model:

Form (title, description, version, language)
 └─ Section (title, section checklist)
     └─ Question (questionId, type, text, config…)
         └─ Roster sub-question (same shape, repeats per row)
LevelKey fields
Formid, title, description, version, language, sections[]
SectionsectionId, title, checklistGuide[], items[]
QuestionquestionId, inputType, questionText, + config blocks below

Questions can be linked to a Core Attribute (e.g. AGE, GENDER, INCOME) from the catalog master_core_attribute. These codes are what HFC rules reference, so checks work consistently across forms.

6 Options & Images

Choice questions (Dropdown, Radio, Checkbox) hold an options array. Each option may be a plain string or an object with an image:

"options": [
  "Plain text option",
  { "type": "image", "label": "Pit latrine", "image": "data:image/png;base64,…" }
]

Option images render beside the label in preview and in the training document — useful for picture-based choices (e.g. toilet/house types) for low-literacy respondents.

7 Validation Rules

Each question can hold a list of validations, each {type, value, message}. Available types:

TypeUse
min_length / max_lengthCharacter-count bounds for text.

Validation enforces format correctness at entry time. For plausibility / cross-field logic that should warn or re-ask (but not strictly block), use HFC form-checks (§11).

8 Skip Logic (Visibility)

Any question can be shown conditionally via visibilityLogic:

"visibilityLogic": {
  "enabled": true,
  "targetQuestion": "q_has_illness",
  "condition": "equals",
  "value": "Yes"
}

Supported conditions:

equals not_equals contains greater_than less_than is_empty is_not_empty

is_empty / is_not_empty don't need a value. The target is referenced by its questionId.

10 Roster (Repeat)

A Roster repeats a block of sub-questions once per “row” (e.g. per household member or per land plot).

  • items[] — the nested sub-questions (any type, fully configured, recursively translatable).
  • iterationQuestionId — links to a Number question whose answer sets how many rows to collect (dynamic count).
  • iterationType / iterationCount — for fixed-count rosters.
In the training document, the roster's own instruction (hint/note) stays directly under its header, and the repeated sub-questions are listed below it.

11 HFC — High-Frequency Checks (Form-Checks)

Per-question quality rules stored in formChecks[]. Each rule fires when its conditions match and then applies an action. This is the data-quality engine that runs on-device during collection.

"formChecks": [{
  "id": "hfc_age_plausible",
  "action": "reask_once",
  "match": "all",
  "severity": "Soft",
  "show_sup": 1,
  "logic": [ { "attr": "q_age", "op": "<", "val": "1" },
             { "attr": "q_age", "op": ">", "val": "120" } ],
  "msg": "Age outside plausible range — please re-confirm."
}]

Action — what happens on match

flag_silentlyRecord a flag, no prompt.
reask_onceRe-ask once, then accept & flag.
reask_and_flagRe-ask; always flag.
blockBlock until corrected.

Severity

Critical Hard Soft Observation

Combinator (match)

all = AND   ·   any = OR

Supervisor

show_sup = surface the flag to the supervisor in review.

Condition operators (logic[].op)

= != > >= < <= contains in empty not_empty

attr references a Core Attribute code or a questionId, so rules can compare across questions (e.g. low income vs. large household).

12 Lookups & Attachments

Forms can carry attached files, managed via Manage Lookup Tables and the attachment API. Supported attachment types:

LOOKUP EXTERNAL_FILE MEDIA_AUDIO MEDIA_VIDEO MEDIA_IMAGE

Lookups provide reference datasets (e.g. village lists) the form can read; media attachments back hints and instructions. Attachments are versioned with the form and can be language-scoped.
