Data Collection App

Purpose: Android app that trains rural users and enables them to easily collect and sync school survey data.

The app will have two main jobs:

  1. Training: Teach the user how to become a data collector using simple, visual-heavy lessons and quizzes in multiple video training modules.
  2. Data Collection: Provide an easy, offline-first form to capture field data and safely sync it when the internet connects.
User Constraints: Design for budget phones, low-internet connectivity, and limited reading skills.

App Flow & Screens

1 Onboarding

Create a highly accessible profile setup flow:

  • Login: Phone number with mock OTP verification.
  • Profile Details: Name, Location, Date of Birth, and Education Level.
  • UX Constraint: Keep forms simple, visual, and easy to navigate for users who struggle with reading.

2 The Main Dashboard (Central Hub)

Create a central dashboard that acts as the home screen once onboarding is complete. It must clearly display the user's current status across the platform:

  • Profile Status: A brief welcome showing they are onboarded.
  • Training Status: A visual indicator showing whether their training is "Pending," "In Progress," or "Completed." (If incomplete, tapping this takes them to the Training Phase).
  • Survey Progress: A summary of their data collection work (e.g., "3 Surveys Pending Sync", "10 Surveys Synced").

3 Training Phase

Users must pass a training sequence before they can collect data.

  • Mock Videos: Show 2-3 training modules (e.g., “How to collect data”, "Approaching the School", “Handling no internet”).
    Note: Do not build a real video player — just use a thumbnail and a "Watch Video" button that fakes completion after a few seconds.
  • The Quiz: After a video finishes, the user must answer a single multiple-choice question correctly to unlock the next module.
  • UX Constraint: Design the quiz for low-literacy users. Rely on visual answers (icons/images), clear color feedback (green for right, red for wrong), and large touch targets.

4 Data Collection (Offline-First)

Once training is passed, unlock the "Survey" feature.

  • The Form: Dynamically load data from sample_survey_schema.json.
  • Offline Storage: Users must be able to fill out and save this form completely offline (e.g., using Room).
  • Background Sync: When the device gets an internet connection, automatically sync the saved surveys in the background (e.g., using WorkManager).

Considerations for the App Engine

1. Visibility Logic

Each question can include a visibilityLogic object that defines whether it should be shown or hidden based on another question’s answer. The logic works only when "enabled": true. If "enabled": false, the question should always be visible.

How it works:

  • Check the user’s input for the question referenced by targetQuestion.
  • Compare that input with the value using the given condition.
  • If the condition is true, show the current question; otherwise, hide it.

2. Validation Rules

Each question can include a validationRules object to specify how user input should be checked before submission. For this exercise, two types of validation exist in the schema:

"validationRules": { "type": "range", "min": "0", "max": "24" } "validationRules": { "type": "text" }

3. FormCheck (HFC) Rules

Some questions can include a formChecks array to specify complex logic checks. For this exercise, you only need to handle "Soft" severity checks like this one:

"formChecks": [ { "id": "hfc_sleep_plausible", "action": "reask_once", "severity": "Soft", "logic": [ { "attr": "q_3", "op": ">", "val": "16" } ], "msg": "That's an unusually high number of hours. Please confirm." } ]

4. Display Structure

When rendering the form from the JSON schema, follow this visual and logical order:

<Survey Title>

    <Section Title>
    <Section Hint / Checklist>

        <Question Text>
        <Question Hint Text>
        [Input Control / Options]
        <Checklist Guide>

    [Action Buttons (e.g., Next, Submit)]
